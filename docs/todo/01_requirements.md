# 要件定義書（TODOアプリケーション V1）

## 1. 目的・対象範囲

本要件定義書は、既存のExpress ＋ TypeScript ＋ EJSで構築されたWebアプリケーションに、TODO管理機能（V1）を追加するための要件を定める。

既存のトップページ（`/`）およびDB接続確認用エンドポイント（`/api/db-check`）はそのまま維持し、ユーザー向けTODO画面を `/todo` に配置する。バックエンドは既存のDB接続処理（`db.ts`）および環境変数 `DATABASE_URL`（Neon PostgreSQL）を利用する。

なお、V1スコープでは認証機能、優先度設定、絞り込み・検索機能、タイトル更新機能は対象外とする。また、実際のファイル配置等の詳細は設計書（`02_design.md`）にて確定する（現時点では要確認）。

* **画面URL**: `/todo`（ファイル配置：要確認）
* **APIベースURL**: `/api/v1/todos`（ファイル配置：要確認）

## 2. 4機能と受け入れ条件

### REQ-01: TODO一覧取得

* **操作**: 画面初期表示時または各種操作後の再描画時に、登録済みのTODO一覧を取得する。
* **入力**: なし（`GET /api/v1/todos`）
* **結果**: 登録されているすべてのTODOを `id` 昇順の配列として取得し、ステータス `200` で返す。データが0件の場合は `data` を空配列 `[]` とする。
* **エラー**: サーバー内部エラー時は `500`（`INTERNAL_ERROR`）、DB接続不可時は `503`（`DB_UNAVAILABLE`）を返す。
* **受け入れ条件**:
  * 画面ロード時に自動で一覧が取得・描画されること。
  * データが0件のとき、GETの `data` が空配列 `[]` になり、画面に「TODOがありません」と表示されること。
* **確認方法**: 画面表示時、および `GET /api/v1/todos` を実行してステータス `200` とレスポンスJSONを確認する。

### REQ-02: TODO新規登録

* **操作**: ユーザーが入力フォームから新しいTODOを登録する。
* **入力**: JSON形式 `{ "title": "文字列" }`（`POST /api/v1/todos`）
* **結果**: 新しいTODOをDBに保存し、生成されたTODOオブジェクト（`id`, `title`, `isCompleted`, `createdAt`）とステータス `201` を返す。
* **エラー**:
  * JSON不正、`title` の欠落、文字列以外の型の場合：`400`（`BAD_REQUEST`）
  * `title` が空白のみ、または101文字以上の場合：`422`（`VALIDATION_ERROR`）
  * サーバー内部エラー・DB利用不可の場合：`500` または `503`
* **受け入れ条件**:
  * 前後の空白を除いて1〜100文字のタイトルが正しく登録され、ステータス `201` と登録データ（初期状態 `isCompleted: false`）が返り、一覧に反映されること。
  * `title` 欠落や空白のみ・101文字以上の入力時に適切なエラーコード（400 / 422）が返り、画面にエラーメッセージが表示されること。
* **確認方法**: 正常値および異常値（欠落・空白のみ・101文字以上）を送信し、ステータスコード・JSON・画面表示を確認する。

### REQ-03: TODO完了状態の部分更新

* **操作**: チェックボックスの操作により、指定したTODOの完了状態（`isCompleted`）を切り替える。
* **入力**: URLパラメータ `id`（1以上の整数）、JSON形式 `{ "isCompleted": boolean }`（`PATCH /api/v1/todos/:id`）
* **結果**: 対象TODOの完了状態を更新し、更新後のTODOオブジェクトとステータス `200` を返す。
* **エラー**:
  * `id` が1以上の整数でない、JSON不正、`isCompleted` がboolean型でない場合：`400`（`BAD_REQUEST`）
  * 指定された `id` のTODOが存在しない場合：`404`（`NOT_FOUND`）
  * サーバー内部エラー・DB利用不可の場合：`500` または `503`
* **受け入れ条件**:
  * チェック操作により対象行の完了状態のみが即座に切り替わり、リロード後も状態が維持されること。
  * 存在しないIDや不正なIDを指定した場合に適切なエラー（404 / 400）が返ること。
* **確認方法**: 完了・未完了の切替操作および存在しないIDへのリクエストを行い、DBとAPIレスポンスを確認する。

### REQ-04: TODO削除

* **操作**: 削除ボタンの押下により、指定したTODOを削除する。
* **入力**: URLパラメータ `id`（1以上の整数）（`DELETE /api/v1/todos/:id`）
* **結果**: 対象のTODOをDBから削除し、ステータス `204`（レスポンス本文なし）を返す。
* **エラー**:
  * `id` が1以上の整数でない場合：`400`（`BAD_REQUEST`）
  * 指定された `id` のTODOが存在しない場合：`404`（`NOT_FOUND`）
  * サーバー内部エラー・DB利用不可の場合：`500` または `503`
* **受け入れ条件**:
  * 削除実行後にステータス `204`（本文なし）が返り、一覧から対象アイテムが消去されること。
  * 存在しないIDを指定した際に `404`（`NOT_FOUND`）が返ること。
* **確認方法**: 削除操作および存在しないIDへのDELETEリクエストを行い、ステータスコードと一覧からの消去を確認する。

## 3. 共通のデータ・エラー条件

### データ仕様

* **`id`**: 1以上の整数（自動採番・主キー）
* **`title`**: 必須文字列（前後の空白を除いて1〜100文字）
* **`isCompleted`**: 真偽値（DB列は `is_completed`、初期値 `false`）
* **`createdAt`**: 作成日時（DB列は `created_at`、初期値 `NOW()`）

### レスポンス・エラー共通仕様

* **成功レスポンス**:
  * `GET` / `POST` / `PATCH`: `{"status": "success", "data": ...}`（0件の一覧は `data: []` で `200`）
  * `DELETE`: `204 No Content`（本文なし。クライアント側でJSON解析しない）
* **エラーレスポンス（統一JSON形式）**:
  `{"status": "error", "code": "...", "message": "...", "details": []}`
  ※SQL文やDB接続文字列などの内部情報は返却しない。
* **エラー条件とステータス・code**:
  * **`400` (`BAD_REQUEST`)**: JSON不正、`title` の欠落、型違い、不正なID形式
  * **`422` (`VALIDATION_ERROR`)**: `title` が空白だけ、101文字以上
  * **`404` (`NOT_FOUND`)**: 対象のIDが存在しない
  * **`500` または `503` (`INTERNAL_ERROR` または `DB_UNAVAILABLE`)**: 内部エラー、DB利用不可

## 4. 環境別確認

公開先（Vercel）のPreview環境およびProduction環境は、ともに同一のNeon PostgreSQLデータベースを参照する。

* **データ運用ポリシー**: 認証なしの公開URLとなるため、個人情報や機密データは一切登録せず、架空の授業用データのみを使用する。
* **環境別の確認方法**:
  1. **Local環境**: `npm run build` および `npm run dev`（または `npm start`）で起動し、`/todo` 画面および `/api/v1/todos` の全操作と既存ルート（`/`, `/api/db-check`）を確認する。
  2. **Preview環境**: `feature/todo-app` ブランチをpushしてPull Requestを作成し、発行されたVercel Preview URLで同様にCRUD操作・エラー処理・既存ルートを確認する。
  3. **Production環境**: `main` ブランチへマージ後、本番URLで同様の確認を実施する（共有DBのため、自分のテスト用データのみを操作・削除する）。
